# 《道德经》公益在线共读平台：初期 Proposal Spec

- 状态：讨论稿 v0.1
- 日期：2026-10-31
- 产品形态：响应式 Web 产品（移动优先），后续可评估 PWA / 原生应用
- 目标读者：发起方、禅桥老师及核心共修组织者、道场领读人、产品与技术团队

## 1. 项目摘要

建设一个以《道德经》共读为入口、以线下共修为连接、以共修内容为长期知识资产的公益平台。首期重点跑通三个核心能力：

1. 让读者在手机上便捷查阅通行王弼本第 1—81 章及基础注释、解读。
2. 以信任为基础沉淀公益共读活动与分享内容；十万次是长期目标。MVP 首要任务是跑通核心产品载体和内容沉淀闭环，不要求优先建设次数展示或后台合并。
3. 让活动记录及经授权的分享按章节沉淀，并提供到场道场发现：默认地图展示，列表按省/市浏览地址。

AI 是建立在可信、可授权、可溯源资料上的后续能力，不应成为首期上线或场次统计的前置条件。系统应保留可替换的模型与检索接口，避免把项目绑定到单一模型供应商。

## 2. 问题与机会

- 经典阅读入口分散，手机上快速定位章节、阅读和回看共修资料不够顺畅。
- 活动散落在微信群和朋友圈，场次、参与情况、活动质量缺少统一且可解释的记录。
- 共修中的经验、领读内容和现场资料难以持续归档、检索、引用或跨城市发现。
- 参与者的个人表达、肖像、声音、位置可能涉及隐私；未经清晰授权的“沉淀”会损害信任。
- AI 若混淆经典原文、注释、个人感悟或未经核实的转述，会造成错误归因和信任风险。

## 3. 产品目标与非目标

### 3.1 初期目标

- 提供适配手机和桌面端的 81 章阅读体验，移动端优先。
- 建立低负担的共读记录提交方式；提交记录先沉淀，重复合并和次数展示后续处理。
- 支持道场、活动、章节、分享内容之间的基本关联。
- 分享内容与公开 profile 默认公开，作者可在发布后隐藏或逻辑删除本人分享；手机号、登录邮箱等认证资料不对外公开。
- 验证参与者是否愿意使用统一入口阅读、登记活动、分享及发现道场。

### 3.2 初期非目标

- 不在首期训练专属大模型或承诺 AI 自动给出权威经义解释。
- 不把上传所有原始音视频作为默认流程；先验证授权、存储成本、审核和整理能力。
- 不把精确实时定位或未经验证的“附近道场排名”作为首期能力。
- 不把浏览量或媒体上传量混作独立共读活动数。
- 不替代线下组织者对共修内容和活动真实性的判断。

## 4. 目标用户与核心任务

| 用户 | 首要任务 | 主要顾虑 |
| --- | --- | --- |
| 普通读者 / 同修 | 查章节、阅读；找到活动或经授权的分享 | 操作复杂、信息不可信、隐私暴露 |
| 领读人 / 分享人 | 发布活动记录和章节相关内容，选择授权范围 | 录入负担、内容被断章取义、撤回困难 |
| 道场组织者 | 维护道场资料、发布或关联共读活动并纠错 | 计数规则不统一、重复提交、资料维护责任 |
| 平台运营者 | 审核争议记录、处理举报、维护内容和统计口径 | 可信度、版权/隐私投诉、运营规模 |
| 核心讲授者 / KOL | 授权管理本人内容及身份标识，查看引用 | 被冒名、错误归因、身份标签被滥用 |

## 5. 首期产品范围

### 5.1 经典阅读

- 收录通行王弼本第 1—81 章；版本、底本来源、文字校对责任人和版权状态须上线前确认并记录。
- 移动端“读书”作为默认入口，以章节目录快速跳转；章节页展示章名（若所用版本有）、原文、基础注释和解读。用户从章节页进入对应章节频道浏览他人分享。“发现”首期只提供道场到场发现，不承载分享洞察信息流或内容推荐。
- 明确区分“经典原文”“注释”“平台编辑说明”“用户共修分享”，显示来源与作者/整理者。
- 支持上一章、下一章、回目录；基础字号调整和阅读进度记忆作为优先体验。
- 搜索、繁简转换、全文对照等列入后续候选，需依据试点反馈排序。

### 5.2 共修活动记录与次数统计

活动记录采用一步提交：已登录用户提交共读记录后即信任，直接新增一条原始记录，不要求活动前预登记、活动后组织者确认、参与者共同确认、签到、二维码或签到管理。平台定位是内容沉淀与发现，不管理线下到场。每次已登录用户提交都计入原始提交数；多人可各自提交同一场活动，MVP 保留每次原始提交，不建设去重合并后台或十万次统计看板。时间由服务端在提交时自动记录，精确到分钟。

活动记录最小字段：

- 活动记录 ID、提交人及账号 ID、服务端提交时间（分钟级）、地点/固定道场 ID、单个共读章节、可选内容关联。
- 可选领读人文字资料及内容形式；不要求参与人数，也不据此确认活动。
- 地点来源（固定道场或临时位置）、修改历史。记录时间即提交时刻，不由用户另行回填。
- 活动记录保留来源和修改历史。MVP 不建设重复地点识别、地点归并或活动合并工作流。

每次提交都形成一条独立原始提交并计入原始提交数。同一活动读多个章节时，按每个章节分别形成提交记录；多名用户提交相同地点和章节也各自计数，不自动合并。十万次是长期目标，不要求外部验证；去重后的活动统计口径留待未来迭代。

后续统计视图可展示累计共读次数、更新时间、口径说明及按月/城市/道场/章节的汇总。数字从后台判定后的独立活动计算；用户提交记录保留原始提交数量，并可在后台合并后调整独立活动数。MVP 阶段以数据沉淀为主，不要求建设统计呈现；合并、更正需保留审计日志。

### 5.3 内容沉淀与道场连接

- 分享内容可关联一章或多章、一个活动及一个道场；活动记录和内容条目是不同对象，避免“有内容才算一场”。
- 内容支持文字、图片、音频和视频；发布后默认公开，发布者可手动隐藏。媒体存储复用家谱项目验证过的技术方案/代码适配方式，不复用其媒体服务实例、存储桶、凭据或数据；道德经项目使用独立媒体存储资源。
- 记录作者、整理者、活动时间、发布/更新时刻、城市级地点及来源；区分“发生时间”和“上传时间”。
- 默认公开：发布内容、公开 profile 身份信息、现场图片/音频/视频均默认公开，发布者可在发布后手动隐藏。手机号、登录邮箱和验证码等认证/找回资料不对外公开。活动提交不强制上传媒体；用户上传并发布后按公开内容处理。临时到场点公开显示到街道级精确位置，由到场维护人标记为可到达地址。
- 分享从读书/章节频道进入；“发现”Tab 不提供跨章节内容、洞察卡片或推荐流。
- 道场发现默认地图模式，并提供与地图结果联动的列表模式；列表按省份/城市查看。移动端地图配可收起列表面板，桌面端地图与列表并排。首期资料梳理以杭州为核心，先覆盖目前已知约 20 个已收录固定道场，并提供浙江省市浏览；该数量不是系统上限。
- 首期地图显示已收录固定道场，不把活动临时地点自动列为可到访道场。地图/省市列表按城市浏览不要求定位授权；临时地点提交仍需授权设备定位。用户可从道场详情跳转高德地图或百度地图导航；MVP 不做产品内路线预计用时。
- 道场公开资料是独立于活动记录的数据，由创建者/主理人负责维护，包括名称、城市、介绍、活动方式、公开联系方式和最近更新时间；可用于未来地图展示道场分布。谁创建谁负责维护。活动可关联固定道场 ID；没有道场 ID 时记录临时地点，由该活动中实际到场的发起人编辑、纠正地点信息，并标记街道级可到达地址，在产品界面公开展示。MVP 不做重复地点识别或地点归并。
- 用户可隐藏或逻辑删除自己的分享；MVP 不提供运营审核后台、人员标签或举报处理工作台。

### 5.4 账号、身份与核心人物标注

- 账号体系纳入 MVP：用户可通过手机号或邮箱注册并登录，邮箱用于密码找回。手机号注册时不要求提供或验证邮箱；用户可在个人资料设置中添加邮箱，验证后才可用于找回。验证码、密码找回和模板适配参考家谱项目已验证的实现，但代码模块与数据库实例独立。用户的产品资料和贡献归属关联其已登录账号。核心讲授者/内容作者标记由后续管理能力处理，不属于 MVP 功能。
- 核心讲授者/内容作者标记应由本人或授权管理员确认；标记仅表示身份/来源经核验，不代表平台为其所有观点背书。
- 内容保留原作者、整理者、授权状态、来源和版本；转录、摘要、AI 派生内容需链接回源内容。
- 建立身份更正、冒名申诉和权限回收流程；重要身份状态变更留痕。

## 6. 用户流程草图

### 6.1 阅读

打开“读书” → 浏览 1—81 章目录 → 进入章节 → 阅读原文/注释/解读 → 进入该章频道浏览他人分享 → 分享详情回链到章节、活动和作者。

### 6.2 登记活动

用户注册账号并登录 → 选择地点/道场并选择单个章节后提交 → 服务端自动记录分钟级提交时间 → 每次提交计入原始提交数；多章活动逐章提交，多个参与人提交均分别保留。临时地点使用设备定位并公开显示到街道级。

### 6.3 发现道场

打开“发现” → 默认查看杭州道场地图 → 切换地图/列表或按省份、城市浏览已收录固定道场 → 打开道场详情查看公开地址 → 跳转高德地图或百度地图导航。地图和省市列表不要求定位授权。

## 7. AI 与 Agent Harness 技术方向

Agent Harness 的工程架构与模块边界详见[Agent Harness 架构方案](./agent-harness-architecture-spec.md)。本节保留 AI / Agent 的产品方向；技术实现以专门架构规格中的已确认基线和待决策项为准。

### 7.1 原则

- 将 Harness 视作编排、工具权限、策略执行、日志与评估层；不要将模型本身等同于 Harness。
- DeepSeek 可作为候选模型之一；通过模型适配层支持按任务切换模型/服务，避免把供应商选择写死在数据模型或内容协议中。
- 数据源、存储、检索、Agent 工具和用户界面分层；首期先做好结构化数据、权限和来源追踪，再启用面向用户的生成能力。
- 经典文本、经核实注释、用户分享、AI 摘要使用不同内容类型和信任标签。检索结果必须遵守原内容权限。

### 7.2 逻辑架构

1. **接入层**：Web 表单、用户主动上传；媒体文件使用独立存储资源，媒体接入技术可参考家谱项目实现。当前不建设 AI 外部数据源连接器或独立 AI 数据接入流水线。后续若启用模型处理，仅针对平台内已获得相应授权的内容另行定义处理范围。
2. **领域数据层**：账号与角色、经典版本/章节、81 个章节频道、内容条目、活动/活动提交、固定道场及临时地点、媒体资产、授权、审核、引用关系、审计事件。
3. **文件与内容处理层**：原始媒体由道德经项目的独立媒体存储资源保存；平台记录对象引用。异步转码、转录、切分等 AI 派生处理暂不纳入当前范围；未来启用时，派生文本需指回原文件和时间位置。
4. **检索层**：结构化数据库负责事实字段与权限。当前不建设 AI 专用全文/向量索引；若未来立项平台内容型 AI，再按确认的数据范围设计可撤回、可删除的检索索引。
5. **Harness / Agent 层**：统一模型适配、检索调用、工具白名单、提示词版本、策略检查、超时与成本控制、运行日志和评测。
6. **应用层**：响应式 Web 读书主入口、章节频道与分享浏览、发现道场地图/省市列表、内容发布、活动记录、道场资料。

### 7.3 AI 首批候选能力（非首期承诺）

以下仅作未来候选；当前不建设 AI 数据接入或平台内容处理能力。

- 经授权音频的转写草稿，供分享者确认后发布。
- 对用户分享生成带来源链接的摘要、主题标签和章节关联建议。
- 基于授权内容回答跨活动问题，并对每条引用展示作者、活动、时间、章节或媒体时间点。
- 未检索到足够依据时明确说明；不得把模型生成的解释伪装成王弼原文、老师原话或平台认证结论。

### 7.4 安全与治理要求

- 检索按用户、角色、内容可见性和授权状态做访问控制；向量索引不能成为权限绕过通道。
- AI 输出区分引用原文、转述和模型生成；回答留存引用 ID、模型/提示版本和必要审计信息。
- 用户上传的材料视为不可信输入，不能直接授予 Agent 新工具或修改权限。
- 对外部模型调用前明确评估个人信息和媒体内容是否出境、是否用于训练及供应商留存政策；提供敏感数据最小化策略。
- 先做人工复核流程与错误反馈，再考虑自动发布或自动建档；AI 不决定活动是否计入公益总场次。

## 8. 数据实体建议（概念级）

| 实体 | 关键关系 / 字段 |
| --- | --- |
| User / Role | 账号、验证状态、角色授予记录 |
| Chapter / TextEdition | 章节号（1—81）、版本、原文、来源、校订版本；章节是稳定的经典目录实体 |
| ChapterChannel | 每章一个预置频道，81 章对应 81 个稳定频道；关联 Chapter，承载该章的分享、话题和讨论。首期不为每场活动创建频道 |
| ContentItem | 分享体悟、金句、生活洞察、文章、话题或评论等内容；作者/整理者、内容类型、正文或媒体引用、可见性、授权状态、创建/更新时间、审核状态 |
| ContentChapterLink | ContentItem 与一个或多个 ChapterChannel 的关联；保存关联来源（用户选择、频道内发布默认关联、运营维护或后续 AI 建议）及确认状态 |
| Gathering / GatheringSubmission | 每个章节维度的共读记录含活动时间（分钟级）、道场/临时地点、章节及状态；多人提交的原始记录保留为 GatheringSubmission，并预留未来按时间、地点、章节识别重复与归并。记录可关联内容和道场，但不等同于频道 |
| Venue / Dojo | 创建者/主理人、名称、城市、介绍、公开位置粒度、联系方式、状态、更新时间；独立维护，可与 Gathering 和 ContentItem 关联 |
| ContentRelation | 内容间的回复、引用、派生、同话题等关系；关系类型受控并记录创建者与时间，避免把社交关系塞入正文字段 |
| MediaAsset | 道德经项目独立媒体存储对象引用、媒体类型、上传者、来源、授权；未来 AI 派生关系另行定义 |
| Consent | 授权主体、用途、范围、期限、撤回时间；可关联 ContentItem、MediaAsset 或身份信息 |
| Citation / Link | 来源内容、目标内容、引用片段/时间点、关系类型 |
| FeedEvent / RecommendationFeedback | 为未来推荐记录可推荐对象（内容/章节频道/活动）、特征/信号版本、曝光/点击等事件，以及不感兴趣/隐藏等用户反馈；具体个性化排序不作为首期上线前置条件 |
| AuditEvent | 操作者、对象、动作、时间、变更前后值/原因 |

### 8.1 实体关系与推荐扩展原则

- `Chapter` 与 `ChapterChannel` 为一对一关系；频道是按章节建立的长期内容空间，不按活动动态创建。
- `ContentItem` 与 `ChapterChannel` 为多对多关系。用户可在章节频道内发布并默认关联当前章，也可将跨章节内容显式关联多个章节。
- `Gathering` 独立于频道和内容；一个共读活动涉及多个章节时按章形成独立记录，共享活动时间、地点等上下文；可关联内容和一个道场。记录允许逐步补充信息，不要求媒体内容。
- “发现”首期只展示固定道场地图和省市列表；章节分享在对应章节频道内按提交时间倒序浏览。跨章节分享/洞察信息流及推荐属于后续范围，不在 MVP 页面实现。
- 后续若增加跨章节内容或活动推荐，可将章节频道内容、活动、用户兴趣与明确授权的互动信号作为候选和排序特征；推荐结果必须保留来源、章节和活动回链。
- 推荐曝光与互动事件需有版本和来源标记，以便解释排序、评估偏差和支持用户纠偏；推荐服务不能越过内容可见性、授权和删除状态。
- 内容关联建议（包括未来 AI 生成的章节/活动关联）先作为待确认建议保存，不应未经作者或运营确认直接改变经典归属或公开推荐关系。

上述实体是概念模型，不预设必须采用单表/多表或某一 ORM 表达方式。落地时应维持稳定 ID、可审计关联、授权过滤和删除传播能力，并避免把“内容归属章节”“活动发生在哪一场”和“频道讨论空间”混为同一个字段或对象。

当前实现基线已确定：Node.js + React 18，生产运行于 Vercel（静态 React 应用 + Serverless Functions），本地用 Express 提供同一组 API handler；数据层使用 Prisma + 云端 PostgreSQL（Neon）。云数据库连接通过 `DATABASE_URL` 和迁移直连 `DATABASE_URL_UNPOOLED` 配置。Agent Harness 作为后续 AI 能力层单独演进，不改变 Web/API/数据库基础架构。

## 9. 成功指标与验证方式

### 9.1 核心指标

- **原始共读记录提交数（MVP）**：每次登录用户成功提交的逐章记录数；重复提交也分别计入，不宣称为去重后的独立场次数。
- **活动记录完整率**：必填活动字段完整的已提交记录占比。
- **阅读任务成功率**：试点用户能否在移动端快速找到指定章节并继续阅读（可通过可用性观察测量）。
- **发布来源完整率**：公开内容具备作者/提交者及来源字段的比例，目标应为 100%；涉及第三方的媒体授权规则需单独明确。
- **提交完成率与回访率**：开始填写后成功提交的比例，以及提交者持续使用情况。未来实现合并后，再评估独立活动数、重复/撤销率等指标。

### 9.2 试点建议

先选少量愿意共同制定口径的杭州道场开展 4—6 周试点；试点规模建议覆盖不同组织方式，而不预设线上/线下活动口径。每周检查登记负担、重复判断、隐私顾虑及参与者是否愿意公开分享。试点前要对照人工台账建立基准，试点后才能判断系统是否提高覆盖率。

## 10. 风险、反例与缓解

| 风险/反例 | 可能后果 | 早期应对 |
| --- | --- | --- |
| 多人信任式提交导致重复记录或误报 | 原始提交数高于独立活动数，合并后累计数变化 | 分开保留原始提交与后台判定的独立活动；展示统计口径和更新时间，合并留审计记录；接受其为内部共修记录 |
| 强制上传照片/录音证明 | 参与者隐私受损、组织者放弃登记 | 活动提交不强制上传媒体；公开含可识别第三方的素材前取得授权或去标识 |
| 默认公开现场素材 | 未同意入镜者被暴露 | 发布前清楚告知公开范围，提供发布后隐藏入口；运营规则需明确第三方素材投诉处理 |
| 地图展示精确地点/实时动态 | 暴露私人聚会地址或成员行踪 | 已确定公开到街道级；维护人标记可到达地址，并提供纠错和隐藏处置 |
| KOL 标签不清晰 | 被冒名或观点错误归因 | 身份认证、来源标记、申诉及权限审计 |
| AI 把分享总结误当经典解释 | 错误传播、权威混淆 | 清晰标注内容类型，逐条引用，低置信时拒答/转人工 |
| 音视频持续积累却无人整理 | 成本增长、检索质量差 | 先小规模试点；定义留存期、处理责任和删除流程 |
| 指标只追求总场次 | 激励刷数、忽视共修质量 | 同时观察记录可信度、参与体验和内容授权完整率 |

## 11. 关键决策与对抗性问题

以下事项尚未定为原则，答案会影响数据模型、活动流程或公开策略。

1. **道场创建者如何交接维护权？** 目前原则是“谁创建谁负责”；若创建者离开或重复创建道场，是否允许主理人/管理员接管或合并？
2. **王弼本和基础注释由谁定稿？** 是否首期只提供一个版本；若后续新增其他整理本或解读，如何标注来源和版本？
3. **未来平台内容型 AI 的责任边界是什么？** 当前不接入 AI 数据；如未来立项，是只检索平台分享还是解释经典？谁审核来源和高影响回答？
4. **公益运营如何持续？** 媒体存储、审核和隐私请求会产生维护成本；由谁维护，哪些内容设定留存期限？

## 13. 建议交付阶段

### 阶段 0：规则和内容准备

确定 MVP 核心闭环、定位与临时地点字段、杭州首批道场资料（目前预计约 20 个，逐个核验地址与坐标）、原文来源和内容发布说明；对照家谱项目核实可复用的媒体技术方案及认证代码边界。账号注册、登录和密码找回在 MVP 纳入实施。MVP 逐次记录原始提交，不做去重合并、十万次统计看板、运营后台或 Agent Harness 工程自动化；地点归并和 AI 数据接入不纳入当前范围。

### 阶段 1：移动优先 MVP

匿名浏览 81 章经文和公开内容；手机号/邮箱注册登录及密码找回；注册用户发布章节分享、提交共读记录、维护道场资料、隐藏自己的内容；从章节频道浏览分享；“发现”默认杭州道场地图，可切换同步列表并按省市查看固定道场地址；临时地点提交时单次授权定位并记录服务端时间。文字及可选媒体发布、高德/百度地图导航跳转。MVP 不含发现洞察信息流、跨章节内容发现、附近定位排序、话题讨论、评论、推荐算法、统计看板、内置路线预计用时、运营后台或 Agent Harness 工程自动化。

### 阶段 2：内容处理与发现

基于使用反馈增加分享引用关系、搜索和更完整的运营看板；AI 转写等媒体处理不在本阶段范围内。

### 阶段 3：受控 Agent 能力

面向平台内容的问答或媒体处理需另行立项，完成数据接入范围、授权、来源引用、人工反馈和评测方案后再决定是否实施；不作为当前阶段承诺。

## 14. 首期验收草案

- 81 章可在手机和桌面浏览，目录可快速定位，章节内容的版本和来源可见。
- 用户可匿名阅读经文和公开内容；注册后可使用手机号或邮箱登录。手机号注册时邮箱为可选资料，验证后可用于找回密码。
- 登录用户可一步提交活动内容记录，无签到要求；多人提交均保留。
- 每次活动记录由服务端自动生成分钟级提交时间；每次提交计入原始提交数，多章按章分别记录，不自动去重或合并。
- 分享可绑定章节/活动/作者，发布后默认公开，发布者可以手动隐藏。
- 固定道场按 ID 关联；无 ID 的自发活动由实际到场的活动发起人编辑/纠正地点并标记街道级可到达地址，形成临时地点记录；MVP 不提供地点归并。
- 使用附近发现和临时地点提交前可授权设备定位；临时地点公开到街道级，由实际到场维护人标记可到达。
- 隐藏内容后立即停止公开访问；逻辑删除后不再出现在公开页面或未来 AI 检索结果中。
- 用户可跳转高德地图或百度地图导航；MVP 不包含内置路线预计用时、运营管理后台或举报处理工作台。

# 《道德经》公益在线共读平台：初期 Proposal Spec

- 状态：产品基线 v1.0
- 日期：2026-11-01
- 更新：2026-11-03
- 产品形态：响应式 Web 产品（移动优先），后续可评估 PWA / 原生应用
- 目标读者：发起方、禅桥老师及核心共修组织者、道场领读人、产品与技术团队

## 1. 项目摘要

建设一个以《道德经》共读为入口、以线下共修为连接、以共修内容为长期知识资产的公益平台。首期重点跑通三个核心能力：

1. 让读者在手机上便捷查阅用户已提供的第 1—81 章文本及基础注释、解读；按数据源的真实版本和校核状态标注。
2. 以信任为基础沉淀公益共读活动与分享内容；十万次是长期目标。MVP 首要任务是跑通核心产品载体和内容沉淀闭环，不要求优先建设次数展示或后台合并。
3. 让活动记录及经授权的分享按章节沉淀，并提供到场道场发现：默认地图展示，列表按省/市浏览地址。

AI 是建立在可信、可授权、可溯源资料上的后续能力，不应成为首期上线或场次统计的前置条件。系统应保留可替换的模型与检索接口，避免把项目绑定到单一模型供应商。

## 2. 问题与机会

- 经典阅读入口分散，手机上快速定位章节、阅读和回看共修资料不够顺畅。
- 活动散落在微信群和朋友圈，场次、参与情况、活动质量缺少统一且可解释的记录。
- 共修中的经验、领读内容和现场资料难以持续归档、检索、引用或跨城市发现。
- 参与者的个人表达、肖像、声音、位置可能涉及隐私；未经清晰授权的“沉淀”会损害信任。
- AI 若混淆经典原文、注释、个人感悟或未经核实的转述，会造成错误归因和信任风险。

## 3. 产品目标与非目标

### 3.1 初期目标

- 提供适配手机和桌面端的 81 章阅读体验，移动端优先。
- 建立低负担的共读记录提交方式；提交记录先沉淀，重复合并和次数展示后续处理。
- 支持道场、活动、章节、分享内容之间的基本关联。
- 分享内容与公开 profile 默认公开，作者可在发布后隐藏或逻辑删除本人分享；手机号、登录邮箱等认证资料不对外公开。
- 验证参与者是否愿意使用统一入口阅读、登记活动、分享及发现道场。

### 3.2 初期非目标

- 不在首期训练专属大模型或承诺 AI 自动给出权威经义解释。
- 不把上传所有原始音视频作为默认流程；先验证授权、存储成本、审核和整理能力。
- 不把精确实时定位或未经验证的“附近道场排名”作为首期能力。
- 不把浏览量或媒体上传量混作独立共读活动数。
- 不替代线下组织者对共修内容和活动真实性的判断。

## 4. 目标用户与核心任务

| 用户 | 首要任务 | 主要顾虑 |
| --- | --- | --- |
| 普通读者 / 同修 | 查章节、阅读；找到活动或经授权的分享 | 操作复杂、信息不可信、隐私暴露 |
| 领读人 / 分享人 | 发布活动记录和章节相关内容，选择授权范围 | 录入负担、内容被断章取义、撤回困难 |
| 道场组织者 | 维护道场资料、发布或关联共读活动并纠错 | 计数规则不统一、重复提交、资料维护责任 |
| 平台运营者 | 审核争议记录、处理举报、维护内容和统计口径 | 可信度、版权/隐私投诉、运营规模 |
| 核心讲授者 / KOL | 授权管理本人内容及身份标识，查看引用 | 被冒名、错误归因、身份标签被滥用 |

## 5. 首期产品范围

### 5.1 经典阅读

- 使用已提供的 81 章数据源；显示其真实来源与校核状态，未经确认不标为王弼本或其他确定底本。
- 移动端“读书”作为默认入口，以章节目录快速跳转；章节页展示章名（若所用版本有）、原文、基础注释和解读。用户从章节页进入对应章节频道浏览该章关联的公开分享。“发现”首期只提供道场到场发现，不承载跨章节分享信息流或全局内容推荐。
- 明确区分“经典原文”“注释”“平台编辑说明”“用户共修分享”，显示来源与作者/整理者。
- 移动端以原文为章节正面：左右滑按阅读页翻阅，跨页到章边界后进入相邻章节；底部常驻非模态浮条，提示当前章注释或频道中按有效阅读数排序的分享，提供收起、半屏、顶部三档，展开可查看注释、本章分享并进入频道。原文末页另提供本章分享摘要/空态与频道入口；支持目录与进度记忆，字号调整收进阅读设置。
- 注释半屏按固定顺序呈现两层，标题分别为「当代注释」与「河上公」，标题下直接显示注释正文。第一层当前先用面向年轻人的白话内容，后续替换为禅桥老师版本；第二层展示河上公古注原文。两层分别保留真实来源与署名，古注须独立确认底本及逐章对应。现有青年易读稿可作第一层候选；现有河上公现代白话转述不能作为古注原文。任一层暂缺时保留该层标题并标注待补，不影响另一层。
- 搜索、繁简转换、全文对照等列入后续候选，需依据试点反馈排序。

### 5.2 共修活动记录与次数统计

活动记录采用一步提交：一次活动对应一个章节记录；已登录用户提交后即信任并保存原始记录。不要求活动前预登记、活动后组织者确认、参与者共同确认、签到、二维码或签到管理。平台定位是内容沉淀与发现，不管理线下到场。每次成功提交均保留为原始记录，其他参与者提交相同活动时也分别保存；MVP 不做重复合并。服务端在提交时自动记录时间，精确到分钟。提交记录用于未来审计，MVP 前端不显示提交数或十万次目标。

活动记录最小字段：

- 活动记录 ID、提交人及账号 ID、服务端提交时间（分钟级）、地点/固定道场 ID、单个共读章节、可选分享关联。
- 每场活动有且仅有一位领读人；记录领读人身份及与账号/公开展示身份的关联。领读人可以不是提交人；无平台账号时按可核验的名称记录，之后可认领/关联。活动记录提交者不自动被当作领读人。
- 不要求参与人数，也不据此确认活动。
- 活动提交记录默认公开；公开层展示必要的提交人基础名称/头像、领读人、章节、分钟级提交时间和地点。认证凭据与手机号/邮箱始终不公开。产品不展示提交总数或十万次成果数字。
- 地点来源（固定道场或临时位置）、修改历史。记录时间即提交时刻，不由用户另行回填。
- 活动记录保留来源和修改历史。MVP 不建设重复地点识别、地点归并或活动合并工作流。

每次提交形成一条独立原始记录；一次活动只记录一个章节，多章节提交不属于 MVP。多名用户提交相同活动时，各自的原始记录均保留，不自动合并。十万次是长期记录目标，不要求外部验证；MVP 不展示提交数，未来再定义审计/去重统计口径。

**后续领域演进方向**：强化线下互动时，应以独立 `GatheringEvent` 作为活动主体，承载发起人、道场、章节、参与者/到场、小组、录音片段与个人收获之间的关系。它不属于 MVP 当前的一人一条原始提交模型；后续 `GatheringSubmission` 可以保留为原始记录，并可选关联活动 ID。活动数量、提交数量、参加覆盖度仍分别定义，不能把到场签到、录音授权、AI 处理授权或内容公开混作同一确认。具体概念见[线下共修流程与自愿记录概念 Spec](./offline-gathering-capture-concept-spec.md)。

后续统计视图可展示累计共读次数、更新时间、口径说明及按月/城市/道场/章节的汇总。数字从后台判定后的独立活动计算；用户提交记录保留原始提交数量，并可在后台合并后调整独立活动数。MVP 阶段以数据沉淀为主，不要求建设统计呈现；合并、更正需保留审计日志。

### 5.3 内容沉淀与道场连接

线下共读通常包含静心、领读分享、“三生万物”三人小组自由交流、小组代表发言、生活故事分享、简短总结与合影。所有共读活动及其记录默认公开；由一位相关人员（领读人、参与者、验证者或助理）用一台设备记录完整共读过程，开始时启动、结束时停止；现场不需要阶段切换状态机或要求参与者操作手机。录音结束后再转写、整理和校对，形成公开记录。细节见[线下共修流程与自愿记录概念 Spec](./offline-gathering-capture-concept-spec.md)。这是后续 Feature，不属于当前 MVP。

- 分享内容可关联一个章节、一个共读记录及一个道场；允许附外部来源 URL/署名，但只展示平台内提交的内容，不抓取或复制全网；活动记录和内容条目是不同对象，避免“有内容才算一场”。
- 内容以文字和音频为优先，图片可作为补充；不鼓励现场视频，MVP 发布表单不主动引导视频上传。发布后默认公开，发布者可手动隐藏。媒体存储复用家谱项目验证过的技术方案/代码适配方式，不复用其媒体服务实例、存储桶、凭据或数据；道德经项目使用独立媒体存储资源。
- 记录作者、整理者、活动时间、发布/更新时刻、城市级地点及来源；区分“发生时间”和“上传时间”。
- 默认公开：发布内容及用户选择附加的现场图片/音频默认公开，发布者可在发布后手动隐藏。作者可以为每条分享选择匿名身份或公开昵称；公开昵称可由用户自行填写（例如与微信相同），不得擅自读取微信资料。匿名时显示通用匿名名和头像，不展示 Profile 昵称/头像；认证账号仍与内容在后台关联以支持管理，产品不能承诺对平台匿名。公开 API 不得泄露手机号、邮箱等账号信息。发布他人可识别的声音/影像前，发布者须确认已取得授权；现场视频不是推荐媒介。临时到场点公开显示到街道级精确位置，由到场维护人标记为可到达地址。
- 分享从读书/章节频道进入；频道内提供章节关联内容流、有效阅读数/最新排序、阅读量、爱心和评论。“发现”Tab 不提供跨章节内容流或全局推荐。
- 道场发现默认地图模式，并提供与地图结果联动的列表模式；列表按省份/城市查看。移动端地图配可收起列表面板，桌面端地图与列表并排。首期资料梳理以杭州为核心，使用已提供的杭州地点资料，并提供浙江省市浏览；初始数据量不是系统上限。
- 首期发现地图与列表展示固定道场及关联有效 POI 的临时地点，清楚标注地点类型；临时地点不因此转为固定道场。地图/省市列表按城市浏览不要求定位授权；临时地点/分享的位置仅用于关联有效 POI 并在地图显示；用户拒绝定位或没有有效 POI 时可不带地理信息提交，章节频道内容照常发布。用户可从道场详情跳转高德地图或百度地图导航；MVP 不做产品内路线预计用时。
- 道场公开资料是独立于活动记录的数据，由创建者/主理人负责维护，包括名称、城市、介绍、常规共读时间规则、是否欢迎初次参与者、是否公开联系方式、公开联系方式和最近更新时间；可用于未来地图展示道场分布。谁创建谁负责维护。活动记录或分享可选关联有效 POI；只有已确认的有效 POI 才在地图展示，无 POI 内容仍可在章节频道访问。MVP 不做重复地点识别或地点归并。道场开放报名方式目前分散在外部微信小程序接龙；**站内活动报名作为 MVP-2 功能**，首期只允许道场资料填写外部公开报名说明或链接（若已有），不建设内部 RSVP。
- 内容创建者可隐藏或逻辑删除本人创建的内容，管理员可管理全部内容；MVP 支持章节分享阅读量、登录用户爱心和评论，并记录内容/评论互动数据。评论默认为单层评论，不提供评论回复、关注/私信或运营审核后台。

### 5.4 账号、身份与核心人物标注

- 账号体系纳入 MVP-1，但实施优先级晚于匿名读书体验和信息框架：用户可通过手机号或邮箱注册并登录。手机号账号可通过短信验证码重置密码，并按账号限制为每滚动 24 小时最多成功重置一次，以控制短信服务成本；邮箱注册账号通过已验证邮箱重置密码。手机号注册时不要求提供或验证邮箱；用户可在个人资料设置中选绑并验证恢复邮箱，作为替代找回方式。验证码、密码找回和模板适配参考家谱项目已验证的实现，但代码模块与数据库实例独立。用户的产品资料和贡献归属关联其已登录账号。核心讲授者/内容作者标记由后续管理能力处理，不属于 MVP 功能。
- 分享公开作者身份遵循逐条选择的匿名/昵称原则。提供约 10 个内置 Q 版《道德经》风格头像；注册流程不要求选头像，先自动分配一个，用户可在 Profile 中更换。匿名分享仍须明确匿名头像与匿名名称的展示方式，避免无意暴露 Profile 昵称。
- 核心讲授者/内容作者标记应由本人或授权管理员确认；标记仅表示身份/来源经核验，不代表平台为其所有观点背书。
- 内容保留原作者、整理者、授权状态、来源和版本；转录、摘要、AI 派生内容需链接回源内容。
- 建立身份更正、冒名申诉和权限回收流程；重要身份状态变更留痕。

## 6. 用户流程草图

### 6.1 阅读

打开“读书” → 浏览 1—81 章目录 → 进入章节 → 阅读原文/注释/解读 → 进入该章频道浏览他人分享 → 分享详情回链到章节、活动和作者。

### 6.2 登记活动

用户注册账号并登录 → 可选关联有效 POI、选择一个章节后提交 → 服务端自动记录分钟级提交时间 → 原始记录保存供后续审计，不展示提交数。一次活动只提交一个章节；多个参与人提交均分别保留。位置仅用于关联有效 POI；拒绝定位或无有效 POI 时允许无地理信息提交。

### 6.3 发现道场

打开“发现” → 默认查看杭州道场地图 → 切换地图/列表或按省份、城市浏览固定道场及有有效 POI 的临时地点 → 打开道场详情查看公开地址 → 跳转高德地图或百度地图导航。地图和省市列表不要求定位授权。

## 7. AI 与 Agent Harness 技术方向

Agent Harness 的工程架构与模块边界详见[Agent Harness 架构方案](./agent-harness-architecture-spec.md)。本节保留 AI / Agent 的产品方向；技术实现以专门架构规格中的已确认基线和待决策项为准。

### 7.1 原则

- 将 Harness 视作编排、工具权限、策略执行、日志与评估层；不要将模型本身等同于 Harness。
- DeepSeek 可作为候选模型之一；通过模型适配层支持按任务切换模型/服务，避免把供应商选择写死在数据模型或内容协议中。
- 数据源、存储、检索、Agent 工具和用户界面分层；首期先做好结构化数据、权限和来源追踪，再启用面向用户的生成能力。
- 经典文本、经核实注释、用户分享、AI 摘要使用不同内容类型和信任标签。检索结果必须遵守原内容权限。

### 7.2 逻辑架构

1. **接入层**：Web 表单、用户主动上传；媒体文件使用独立存储资源，媒体接入技术可参考家谱项目实现。当前不建设 AI 外部数据源连接器或独立 AI 数据接入流水线。后续若启用模型处理，仅针对平台内已获得相应授权的内容另行定义处理范围。
2. **领域数据层**：账号与角色、经典版本/章节、81 个章节频道、内容条目、活动/活动提交、固定道场及临时地点、媒体资产、授权、审核、引用关系、审计事件。
3. **文件与内容处理层**：原始媒体由道德经项目的独立媒体存储资源保存；平台记录对象引用。异步转码、转录、切分等 AI 派生处理暂不纳入当前范围；未来启用时，派生文本需指回原文件和时间位置。
4. **检索层**：结构化数据库负责事实字段与权限。当前不建设 AI 专用全文/向量索引；若未来立项平台内容型 AI，再按确认的数据范围设计可撤回、可删除的检索索引。
5. **Harness / Agent 层**：统一模型适配、检索调用、工具白名单、提示词版本、策略检查、超时与成本控制、运行日志和评测。
6. **应用层**：响应式 Web 读书主入口、章节频道与分享浏览、发现道场地图/省市列表、内容发布、活动记录、道场资料。

### 7.3 AI 首批候选能力（非首期承诺）

以下仅作未来候选；当前不建设 AI 数据接入或平台内容处理能力。

- 经授权音频的转写草稿，供分享者确认后发布。
- 对用户分享生成带来源链接的摘要、主题标签和章节关联建议。
- 基于授权内容回答跨活动问题，并对每条引用展示作者、活动、时间、章节或媒体时间点。
- 未检索到足够依据时明确说明；不得把模型生成的解释伪装成王弼原文、老师原话或平台认证结论。

### 7.4 安全与治理要求

- 检索按用户、角色、内容可见性和授权状态做访问控制；向量索引不能成为权限绕过通道。
- AI 输出区分引用原文、转述和模型生成；回答留存引用 ID、模型/提示版本和必要审计信息。
- 用户上传的材料视为不可信输入，不能直接授予 Agent 新工具或修改权限。
- 对外部模型调用前明确评估个人信息和媒体内容是否出境、是否用于训练及供应商留存政策；提供敏感数据最小化策略。
- 先做人工复核流程与错误反馈，再考虑自动发布或自动建档；AI 不决定活动是否计入公益总场次。

## 8. 数据实体建议（概念级）

数据库设计尚未启动；实体、字段、约束和索引在 MVP-1 产品基线确认后另行设计评审。本节中的多章节关联、内容关系、推荐及 Consent 等概念应按下文阶段边界理解，不代表全部进入 MVP。

| 实体 | 关键关系 / 字段 |
| --- | --- |

### 8.1 章节频道实体关系、有效阅读数排序与数据飞轮原则

- `Chapter` 与 `ChapterChannel` 为一对一关系；频道是按章节建立的长期内容空间，不按活动动态创建。
- MVP 的 `ContentItem` 只关联一个 `Chapter`；在章节频道内发布时默认关联当前章。频道聚合平台内公开发布、明确关联到本章的分享；可附外部来源链接并保留作者/来源信息。跨章节关系表是未来扩展。
- `GatheringSubmission` 是每位提交者的一条原始单章节记录，不另建合并后的 Gathering 主表；可被分享引用，但不等同于频道。
- 一条提交可关联固定道场、专属临时地点或不关联地点；多人记录不合并，临时地点不归并。
- “发现”首期展示固定道场和关联有效 POI 的临时地点地图及省市列表；章节分享在对应章节频道浏览，默认按有效阅读数排序，并可切换最新排序。排序限于当前章节频道，不是跨章节或个性化推荐。
- 分享默认按有效阅读数降序；爱心和评论只作为互动计数展示，不参与主排序。频道提供“最新”替代视图。有效阅读数不代表内容质量或经义权威度。
- 互动信号必须按内容状态过滤；隐藏/逻辑删除内容及其评论不参与公开排序。曝光与有效阅读分开埋点；同一访客对同一分享按 Asia/Shanghai 自然日去重，同日最多计一次、次日可再计一次；触发条件、访客键、异常流量和并列顺序在实现前定义。
- 评论按时间顺序展示；记录评论正文、作者、章节、所属分享和互动时间，使未来可评估哪些讨论值得沉淀。MVP 不对单条评论计算活跃分，也不提供评论爱心/回复；未来若要排序活跃评论，需新增对应互动信号。MVP 不自动摘要、不训练模型、不向第三方模型传输评论；后续 AI/数据挖掘需先定义授权、脱敏、删除传播和人工评估规则。

上述实体是概念模型，不预设必须采用单表/多表或某一 ORM 表达方式。落地时应维持稳定 ID、可审计关联、授权过滤和删除传播能力，并避免把“内容归属章节”“活动提交记录”和“频道讨论空间”混为同一个字段或对象。

当前实现基线已确定：Node.js + React 18，生产运行于 Vercel（静态 React 应用 + Serverless Functions），本地用 Express 提供同一组 API handler；数据层使用 Prisma + 云端 PostgreSQL（Neon）。云数据库连接通过 `DATABASE_URL` 和迁移直连 `DATABASE_URL_UNPOOLED` 配置。Agent Harness 作为后续 AI 能力层单独演进，不改变 Web/API/数据库基础架构。

## 9. 成效定义、北极星指标与数据回流

### 9.1 价值链与北极星候选

项目的北极星不是营收、页面流量或十万条平台记录，而是参与者是否获得了可带回生活的新视角，并愿意继续共读与分享。产品的作用假设为：接触经文/道场 → 参与共读 → 感到被倾听或获得新视角 → 在工作生活中尝试一个具体行动 → 将体会反馈到对应章节，帮助后来者继续学习。

**北极星候选：月度自愿反馈参与者数**——一个自然月内，至少一次在对应章节频道发布了共读所得（文字或音频）的去重参与者数。须同时报告反馈人数占可估计参与者人数的比例、匿名分享占比及后续回访，不把反馈人数直接解释为“被帮助人数”。MVP 初期不强制问卷、不把投稿作为参与共读的门槛；先以自愿分享和小规模访谈验证指标与真实收获的相关性。

### 9.2 四类不同口径

| 维度 | 定义 | 用途与边界 |
| --- | --- | --- |
| 活动数 | 经后台未来去重判定后的独立共读活动数；原始提交不能直接当活动数 | 反映共读活动覆盖与频率；MVP 不做合并、不展示此数 |
| 提交数 | 成功保存的原始共读活动提交条数 | 反映平台记录链路是否仍被使用；同场多人提交分别计数，不能代表独立活动或参与人数 |
| 参与覆盖度 | 在明确口径和观察周期内参与共读的去重人数，以及覆盖的道场/城市/新参与者分布 | 反映服务触达广度；因 MVP 不管理签到，平台记录无法完整代表实际参与者，需标注估计来源/覆盖局限 |
| 体验结果 | 自愿反馈中报告获得新视角、感到被倾听、愿意尝试具体行动等结果 | 用来评估人本价值；不宣称治疗焦虑或替代专业支持，报告样本量、反馈率与自选择偏差 |

### 9.3 正向反馈飞轮与回流闭环

共读体验 → 自愿分享体会（可匿名）→ 按章节沉淀 → 后来者找到相关经验并参与 → 产生新的体验与分享 → 反馈给道场/产品改进。闭环的每一步都要有可观察证据：内容是否被阅读、是否帮助发现适合加入的道场、是否带来新参与者、分享者是否愿意再次反馈。数据回流应支持改善共读体验和内容组织，不将个人脆弱经历用于推荐操纵、商业画像或未经同意的 AI 训练。

MVP 先保存必要业务数据和分享内容关联；匿名化、最小化地进行试点复盘。参与者覆盖、体验结果的规范化采集及仪表盘需在后续明确告知、退出方式、保留期限和分母定义后建设。活动提交数、内容互动量只能作为诊断指标，不能取代体验结果。

### 9.4 MVP 验证方式

- 阅读任务成功率：试点用户能否在移动端快速找到指定章节并继续阅读。
- 自愿反馈：记录章节分享的发布、阅读及再次分享情况；体验问法先采用可选的非临床表达，例如“这次共读是否带给你一个看问题的新角度？”和“你愿意尝试什么小行动？”，避免强迫披露敏感经历。
- 参与覆盖：通过道场/活动试点台账估计覆盖，不从内容作者数推断全部到场人数。
- 道场发现：观察详情访问到公开报名渠道点击/新手联系的转化；站内报名属于 MVP-2。
- 所有指标明确口径、周期、分母、样本覆盖和责任人。小样本先定性复盘，不以未经验证的数字做绩效目标。

### 9.2 试点建议

先选少量愿意共同制定口径的杭州道场开展 4—6 周试点；试点规模建议覆盖不同组织方式，而不预设线上/线下活动口径。每周检查登记负担、重复判断、隐私顾虑及参与者是否愿意公开分享。试点前要对照人工台账建立基准，试点后才能判断系统是否提高覆盖率。

## 10. 风险、反例与缓解

| 风险/反例 | 可能后果 | 早期应对 |
| --- | --- | --- |
| 多人信任式提交导致重复记录或误报 | 原始提交数高于独立活动数，合并后累计数变化 | 分开保留原始提交与后台判定的独立活动；展示统计口径和更新时间，合并留审计记录；接受其为内部共修记录 |
| 强制上传照片/录音证明 | 参与者隐私受损、组织者放弃登记 | 活动提交不强制上传媒体；公开含可识别第三方的素材前取得授权或去标识 |
| 默认公开现场素材 | 内容可能需要事后更正或隐藏 | 发布前清楚说明默认公开范围，提供发布后隐藏入口和更正流程 |
| 地图展示精确地点/实时动态 | 暴露私人聚会地址或成员行踪 | 已确定公开到街道级；维护人标记可到达地址，并提供纠错和隐藏处置 |
| KOL 标签不清晰 | 被冒名或观点错误归因 | 身份认证、来源标记、申诉及权限审计 |
| AI 把分享总结误当经典解释 | 错误传播、权威混淆 | 清晰标注内容类型，逐条引用，低置信时拒答/转人工 |
| 音视频持续积累却无人整理 | 成本增长、检索质量差 | 先小规模试点；定义留存期、处理责任和删除流程 |
| 指标只追求总场次 | 激励刷数、忽视共修质量 | 同时观察记录可信度、参与体验和内容授权完整率 |

## 11. 关键决策与对抗性问题

以下事项尚未定为原则，答案会影响数据模型、活动流程或公开策略。

1. **道场创建者如何交接维护权？** 目前原则是“谁创建谁负责”；若创建者离开或重复创建道场，是否允许主理人/管理员接管或合并？
2. **后续版本与注释如何定稿？** 首期使用已提供数据并保留来源与现有校核状态；后续若新增整理本或解读，如何标注来源和版本？
3. **未来平台内容型 AI 的责任边界是什么？** 当前不接入 AI 数据；如未来立项，是只检索平台分享还是解释经典？谁审核来源和高影响回答？
4. **公益运营如何持续？** 媒体存储、审核和隐私请求会产生维护成本；由谁维护，哪些内容设定留存期限？
5. **匿名分享的真实边界是什么？** 匿名只遮蔽公开昵称/头像，账号仍关联内容；若分享者上传可识别声音、提到工作地点/经历或被领读人身份关联，旁人仍可能推断其身份。是否需对音频提供变声/仅转写选项，MVP 至少要用清晰提示避免承诺“完全匿名”。
6. **默认公开内容如何保持可信？** 活动与现场媒体默认公开；需要明确记录来源、人工校对、发布后更正和隐藏流程，避免转写错误被当作原话传播。
7. **月度自愿反馈数是否可获得合理分母？** 没有签到和参与者名册时，反馈人数可以可靠计算，但“反馈率”分母只能靠试点台账估计；若分母不可比，北极星先报告反馈人数和访谈证据，不把反馈率列为绩效目标。

### 11.1 章节频道互动的反向审视

- **活跃度不等于质量**：有效阅读数可能受先发优势和异常流量影响；需定义去重和异常流量规则，并提供最新排序。有效阅读数按自然日去重并累计；曝光、访客键、阅读触发条件和异常流量处理口径在实现前定义。
- **评论形成治理负担**：评论提供作者自删、隐藏内容过滤和基础限流；管理员可直接管理全部内容。
- **数据飞轮不是默认 AI 授权**：MVP 可积累互动事件和评论数据用于产品指标；单条评论活跃排名留待未来具备爱心/回复等信号后再决定。任何模型训练、生成摘要或内容挖掘均需单独授权、用途说明和删除传播。
- **“全网内容”边界**：首期按平台内发布且明确关联章节的内容设计，可附原网页链接/来源；不主动抓取或复制全网内容。若产品需要全网聚合，需另行评估版权、来源校验、去重、抓取许可和下架机制。

## 13. 建议交付阶段

### 阶段 0：规则和内容准备

确定 MVP 核心闭环、定位与临时地点字段、已提供的杭州首批道场资料（按来源与核实状态导入）、原文来源和内容发布说明；对照家谱项目核实可复用的媒体技术方案及认证代码边界。账号注册、登录和密码找回在 MVP 纳入实施。MVP 逐次记录原始提交，不做去重合并、十万次统计看板、运营后台或 Agent Harness 工程自动化；地点归并和 AI 数据接入不纳入当前范围。

### 阶段 1：移动优先 MVP

匿名浏览 81 章经文和公开内容；手机号/邮箱注册登录及密码找回（优先级晚于读书和信息框架）；注册用户发布章节分享、提交共读记录、维护道场资料、隐藏自己的内容；从章节频道浏览分享；“发现”默认杭州道场地图，可切换同步列表并按省市查看固定道场及有有效 POI 的临时地点地址；地点/POI 为可选关联，拒绝定位时仍可提交章节内容。文字及可选媒体发布、高德/百度地图导航跳转。MVP-1 不含站内报名（MVP-2 实现）或发现洞察信息流、跨章节内容发现、附近定位排序、话题系统、楼中楼回复、全局推荐算法、独立统计看板、内置路线预计用时、运营后台或 Agent Harness 工程自动化。

### 阶段 2：内容处理与发现

基于使用反馈增加分享引用关系、搜索和更完整的运营看板；AI 转写等媒体处理不在本阶段范围内。

### 阶段 3：受控 Agent 能力

面向平台内容的问答或媒体处理需另行立项，完成数据接入范围、授权、来源引用、人工反馈和评测方案后再决定是否实施；不作为当前阶段承诺。

## 14. 首期验收草案

- 81 章可在手机和桌面浏览，目录可快速定位，章节内容的版本和来源可见。
- 用户可匿名阅读经文和公开内容；注册后可使用手机号或邮箱登录。手机号注册时邮箱为可选资料；手机号账号可通过短信验证码重置密码，每滚动 24 小时最多成功重置一次，也可使用已验证恢复邮箱找回。
- 登录用户可一步提交活动内容记录，无签到要求；多人提交均保留。
- 一次活动提交一个章节；服务端自动生成分钟级提交时间；每次提交保存为一条原始记录，多人提交分别保留；不自动去重或合并，前端不展示提交数。
- 分享可绑定章节/活动/作者，发布后默认公开，发布者可以手动隐藏。
- 地点可选；固定道场按 ID 关联，临时地点由发起人编辑并确认有效 POI；MVP 不提供地点归并。
- 位置仅用于有效 POI 地图展示；固定道场地图/省市列表无需定位；拒绝定位或无有效 POI 时可不关联地点并继续发布章节内容。
- 隐藏内容后立即停止公开访问；逻辑删除后不再出现在公开页面或未来 AI 检索结果中。
- 用户可跳转高德地图或百度地图导航；MVP 不包含内置路线预计用时、运营管理后台。

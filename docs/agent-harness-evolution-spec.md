# Agent Harness：自进化方案（预留）

- 状态：方向设计稿 v0.2，当前仅作后续架构预留
- 日期：2026-10-31
- 适用项目：《道德经》公益在线共读平台
- 依赖：[Agent Harness 架构 Spec](./agent-harness-architecture-spec.md)、[技术架构 Spec](./technical-architecture-spec.md)、[数据库表结构设计](./database-schema-spec.md)
- 范围：未来的问题发现、候选改进、评测与受控交付；不纳入当前 MVP 实现

## 1. 目标与原则

Agent Harness 的自进化能力是本项目对“自动发现问题并持续优化”的未来方案，当前不属于 MVP-1/2 实施范围。它不是一个拥有生产权限的自主开发者，而是一条把信号转为可审阅改进的工程闭环：

```text
用户/系统信号 → 归类与证据 → 候选问题/需求 → 优先级与授权检查
→ 隔离开发或分析 → Judge 评测 → 人工批准 → 灰度/发布 → 指标回看与回滚
```

核心约束：

- 当前 MVP 不采集新的产品分析事件、不建设许愿墙、不建设自动修复、不对用户沉淀内容做模型挖掘；只保留未来适配点和本文的决策边界。
- 原始信号不等于任务授权。Agent 只能处理被明确纳入范围、通过权限检查和脱敏的数据。
- 用户数据分析、用户内容挖掘、工程代码执行是三种不同用途，必须有分离的策略、数据集和评测。
- 系统可自动生成分析、工单、测试和代码候选；生产写入、合并、上线及授权策略变更须由人批准。
- 每个候选改进都应能追溯来源信号、Spec/策略版本、评测结果、审阅人、发布版本和回滚点。

## 2. 问题发现来源与优先级

按用户给出的优先级排序。P0/P1 是未来首批候选；P2、P3 需在前序能力和授权制度成熟后再评估。此优先级不改变当前 MVP 范围。

| 优先级 | 来源 | 未来用途 | 进入 Agent Harness 的条件 | 当前状态 |
| --- | --- | --- | --- | --- |
| P0 | 业务核心链路产品分析 | 观察用户动线、关键行为、漏斗转化与流失位置，形成可验证的问题假设 | 先批准事件字典、同意/告知、最小化采集、保留期和供应商/部署选择；仅使用聚合指标或授权的去标识事件 | 只预留事件契约；MVP 不新增埋点平台 |
| P1 | 用户建议模块 | 收集产品建议并持久化为 VOC 数据，供后续人工或自动化处理 | 明确公开范围、身份策略、滥用处理和用户可见状态；原始文本不得直接作为 Agent 指令 | MVP-1 建议入口与数据库沉淀；自动化分析后续单独启用 |
| P2 | 异常、错误和崩溃 | 聚合异常、定位影响范围、生成复现步骤/测试和修复候选 | 错误上报需脱敏；具备隔离执行、回归评测、审阅和回滚；低风险分类经独立批准后才可扩大自动化 | 候选能力，不属于 MVP |
| P3 | 共读内容数据挖掘 | 对获准使用的分享体验做群体层面的主题/趋势综合，生成内部研究假设 | 另行取得明确用途授权，限定内容范围、匿名化/聚合阈值、删除传播、外部模型处理和输出复核 | 不接入、不索引、不训练、不生成派生物 |

### 2.1 产品分析预留原则

未来分析系统需支持标准事件接口，并能替换自托管或外部分析实现；在数据驻留、成本、跨境处理和同意要求未决前，不锁定具体供应商。业务代码只调用项目内的 `ProductAnalytics` 抽象，不直接依赖某个平台 SDK。

建议事件先采用版本化、字段白名单的契约：`event_id`、`event_name`、`schema_version`、`occurred_at`、匿名会话或内部伪名主体、页面/功能上下文、允许的属性。不得传输手机号、邮箱、认证令牌、自由文本正文、媒体内容或精确定位。身份关联须经单独决策并可禁用。

未来核心漏斗可从真实用户旅程定义，例如：打开章节 → 阅读/保存进度 → 注册/登录 → 发布章节分享或提交共读 → 后续互动。具体漏斗、匿名到登录的连接规则和转化窗口需用产品问题验证后确定，不将页面浏览量直接等同于价值。

可度量指标包括各阶段独立用户数、阶段转化率、阶段间耗时、流失比例、事件丢失/重复率，以及按客户端版本/设备类别切片后的异常差异。埋点质量本身需有契约校验和版本兼容监控。

### 2.2 许愿墙闭环预留原则

未来愿望至少区分：`SUBMITTED`、`NEEDS_CLARIFICATION`、`TRIAGED`、`PLANNED`、`IN_PROGRESS`、`SHIPPED`、`DECLINED`、`DUPLICATE`。用户提交原文与公开展示授权分开记录；不默认公开署名或把内容授权给模型。支持/投票应限制重复刷票，并作为需求信号之一，而非自动开发排序的唯一依据。

Agent Harness 只消费经审核的结构化需求摘要、影响面、支持度聚合和验收条件，不直接把用户自由文本作为可执行指令。交付状态可回写建议记录，但需保留人工确认和面向用户的更新记录。

### 2.3 错误修复闭环预留原则

异常服务可提供分组后的错误类型、受影响版本/页面、发生频率和脱敏堆栈。Agent Harness 在隔离工作区生成复现或回归测试，提出补丁并运行项目规定的检查。合并前必须通过 Judge 的回归、安全、资源和代码所有权规则，并由维护者审阅。

任何允许自动合并/发布的后续试点都必须限定在可回滚、低影响、无数据迁移/权限/认证/支付/授权策略变更的类别，并有独立熔断阈值。崩溃自动修复若改坏认证、数据可见性或删除语义，影响可能大于原故障，因此“测试通过”不能单独构成上线授权。

### 2.4 共读体验挖掘预留原则

此能力与工程自动化 Harness 分开治理。原始用户分享、评论、音视频及其派生摘要均属于受保护数据。仅在用途明确授权后，使用最小必要、去标识/群体聚合的材料进行周期性综合；不得用于训练模型，除非用户另行明确授权且另有批准。需提供来源覆盖说明、隐私风险检查、删除传播和人工发布审阅；不得输出可识别个人的推断或把模型生成主题当作经文权威解释。

## 3. Agent Harness 接入架构

```text
产品分析 Adapter ─┐
许愿墙 Adapter ───┼→ Signal Gateway → 去重/脱敏/分类 → Evidence & Issue Queue
错误监控 Adapter ─┤                                      ↓
授权数据研究 Adapter┘                   Direction → Judge → Evolution
                                                       ↓
                                            隔离 Worker / 受限工具
                                                       ↓
                                      评测报告 → 人工批准 → 灰度/回滚
```

- **Signal Gateway**：校验来源签名/权限、schema 版本、速率和保留规则；来源系统不能直接向 Agent 注入工具调用或系统指令。
- **Issue Queue**：保存经筛选的候选问题和证据引用；按来源类型施加不同数据访问策略。
- **Direction / Judge / Error / Evolution / Resource Governor**：复用 [Agent Harness 五大模块](./agent-harness-architecture-spec.md)；业务分析与用户内容研究使用各自隔离的数据策略。
- **隔离执行**：代码修复使用临时工作区和受限命令；数据研究使用只读、最小化数据集。两者不得共享任意工具或长期缓存。
- **发布接口**：未来只提交待审 PR/发布候选。上线、状态回写及回滚由受控服务执行，审计批准人及目标版本。

架构上预留稳定 Adapter 契约和事件版本，不预先建设微服务、队列或专用数据库。实际吞吐、重试和隔离需求明确后再选型；Agent Harness 运行记录不得与业务内容表混作一个 AI 知识库。

## 4. 自动化阶段与放行门槛

| 阶段 | 能力 | 自动化边界 | 放行门槛 |
| --- | --- | --- | --- |
| 0：预留 | 事件/信号契约、数据边界和接口设计 | 不采集、不执行 | 当前阶段 |
| 1：可观测 | 经批准的产品分析和错误监控；许愿墙人工分诊 | 自动汇总与告警，不自动改代码 | 埋点质量、隐私/权限审查、指标定义 |
| 2：建议 | Agent Harness 生成问题摘要、优先级建议、验收条件/测试草案 | 人工确认需求后进入工程任务 | 来源证据可核查，误报率可测，人工评审 |
| 3：候选开发 | 隔离工作区创建补丁/PR并运行评测 | 不自动合并或部署 | 基线对比、回归/安全评测、预算与回滚方案 |
| 4：有限自动交付 | 仅限已批准的低风险变更类别，灰度并自动监测 | 受限自动合并/发布，可随时熔断 | 独立风险批准；连续运行质量达到预设门槛；自动回滚验证 |

每一阶段均需有 feature flag、预算上限、运行时限、最大重试、人工接管、审计和停止开关。阶段晋级不能由 Agent 自己决定。

## 5. 成效度量

指标需按信号类型分别计算，不能用一个“自动化率”掩盖质量问题：

- **发现质量**：有效问题占比、重复问题率、被人工采纳比例、从信号到确认问题的时间。
- **产品漏斗**：各关键步骤转化率、流失率与耗时；同时报告埋点完整率、重复率和事件 schema 错误率。
- **需求闭环**：愿望审核时间、进入计划比例、交付比例、状态同步时延、用户反馈；不以票数单独决定优先级。
- **修复质量**：候选采纳率、评测通过率、回归/回滚率、平均修复周期、每个有效修复成本。
- **数据研究质量**：经人工验证的主题稳定性、覆盖面、隐私审查通过率；结果只能作为研究假设，不作个体结论。
- **总护栏**：未经授权数据访问次数为零；越权工具调用为零；严重事故、数据暴露、自动回滚和预算超限均单独上报。

开始试点前须为每项指标指定分母、时间窗、责任人和阈值；没有基线的指标先观察，不以未经校准的数值驱动自动发布。

## 6. 未来持久化边界

当前数据库 Spec 的业务表保持 MVP 范围，不因本稿新增迁移。未来单独立项后再评估最小增量，候选实体包括：

- `ProductEvent`（或转交分析供应商）：仅版本化白名单事件/同意状态；优先避免在业务数据库长期保存逐用户行为明细。
- `Wish`、`WishStatusHistory`、`WishSupport`：愿望、状态变更审计和受限支持关系；原文、公开授权及模型处理授权分开管理。
- `SignalIssue`、`SignalEvidenceRef`：问题候选及对来源的稳定引用；不复制完整用户分享、日志或媒体。
- `AutomationProposal`、`ProposalEvaluation`、`ApprovalRecord`、`ReleaseRecord`：候选变更、评测、人工批准和上线/回滚审计。
- `DataUseGrant`（若未来确有用户内容挖掘）：明确主体、材料范围、用途、有效期、撤回和派生物清理状态；它不能由通用发布确认推导。

这些概念不等于当前已批准的表结构或授权方案。未来实现前要重新评估数据保留期限、访问角色、删除/撤回传播和独立数据库/schema 的必要性。

## 7. 关键风险与决策门

1. **漏斗测量可能造成过度追踪**：优先测功能步骤的聚合转化，避免把匿名行为与实名账号永久绑定；在采集前明确告知、退出方式和保留期。
2. **许愿墙票数会偏向更活跃群体**：把支持数与用户影响、产品方向、开发成本、无障碍/安全风险结合，不能直接按票数自动开工。
3. **自动修复可能扩大事故**：Agent 提交的代码即使能通过生成的测试，也可能遗漏数据权限、认证或删除语义回归；Judge 需要独立维护的评测与人工审批。
4. **“Dreams”类综合有隐私与代表性风险**：群体总结可能暴露少数人的经历，也可能把少量样本误说成普遍事实。采用最小群体阈值、来源覆盖说明及人工复核；授权与删除链路不清晰时不启用。

**当前决策**：先保留接入契约、模块边界和放行机制；本 MVP 不落实埋点供应商、许愿墙、错误自动修复或用户数据挖掘。进入下一阶段前，应优先确认分析数据的匿名/登录关联规则及数据保留期限；进入 P3 前再单独确认内容用途授权方案。

## 8. 对抗性问题

如果漏斗显示某类共读分享“转化率低”，而用户并未同意把可识别行为与账号绑定，Agent Harness 是否应被允许把匿名路径归因到某个具体用户并自动改造流程？本方案的默认答案是“不允许”：分析应先以聚合、去标识证据形成假设，产品负责人确认目标后再进入开发；不能通过提高追踪强度来弥补因果证据不足。

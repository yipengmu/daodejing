# 《道德经》公益共读平台：技术编码计划书

- 状态：MVP-1 基线候选 v0.2
- 日期：2026-11-01
- 更新：2026-11-03
- 依据：[Proposal Spec](./proposal-spec.md)、[页面流程 Spec](./product-page-flow-spec.md)、[技术架构 Spec](./technical-architecture-spec.md)、[设计指导 Spec](./design-guidelines-spec.md)
- 范围：MVP 技术工作拆分、交付顺序、依赖和验收口径；不包含代码实现

## 1. 编码目标

交付一个移动优先、适配桌面端的响应式 Web MVP，跑通匿名阅读与发现、账号注册登录、章节分享、共读记录、道场资料及定位发现闭环。

编码前核对并沿用家谱项目已验证的 Node.js、React、Vercel、Prisma、认证和媒体技术实现方式；为道德经项目建立独立 Neon 数据库、独立环境密钥和独立媒体资源。认证与媒体代码/方案可以复用，服务实例与业务数据不共享。

本计划不包含面向用户的 AI、Agent Harness 工程自动化、运营管理后台、人员标记界面、话题讨论/楼中楼、跨章节推荐算法、独立次数看板、活动合并、产品内路线预计用时或完整导航。

## 2. MVP 范围和关键约束

### 包含

- 匿名浏览已提供的 1—81 章原文、来源信息和公开分享，按种子的真实来源及校核状态展示，不擅自标记为王弼本。优先交付读书体验与信息框架，再交付登录注册和写入能力。
- 手机号或邮箱注册与登录；手机号注册不要求提供邮箱。个人资料页可选绑定并验证找回邮箱。
- 对外分享卡片仅展示基础名称和头像；提供约 10 个内置 Q 版《道德经》风格头像。手机号、登录邮箱、验证码等认证/找回信息始终私有，不从公开内容 API 返回。
- 登录用户发布章节分享、阅读/爱心/评论互动、提交共读记录、创建/维护本人道场资料、管理本人内容；管理员可管理所有用户创建的内容。账号删除等逆向流程不属于 MVP-1，数据默认持续保留。
- 章节频道展示本章关联的站内公开分享，默认按有效阅读数排序并可切换最新；爱心和单层评论为展示/互动能力，不参与主排序。“发现”Tab 只承载道场地图/列表与省市筛选。
- 产品提供建议入口，提交内容自动沉淀为数据库 VOC 记录；自动化分析和处置属于后续 Harness 能力，不是 MVP-1。
- 一次活动提交一个章节；服务端以分钟级时间记录每次提交。每次登录用户提交均保留一条原始记录，其他参与者重复提交也保留；不做去重。MVP 页面不展示提交数，十万次目标留给后置审计。
- 用户隐藏内容后立即从公开读取接口排除；逻辑删除后保留必要 tombstone/关联，不再公开提供，也不得进入未来 AI 检索。
- 文字分享优先，支持音频和图片附件；不鼓励现场视频，MVP 不主动引导视频上传。媒体大小/时长/格式限制在 Phase 0 按独立存储方案定值。媒体数据与数据库均使用道德经项目独立资源。
- 分享人可逐条选择匿名身份或公开昵称；公开只展示基础名称和头像，账号联系方式不公开。匿名是对其他用户隐藏身份，不是对平台/数据库匿名，发布前需清楚说明。
- 道场导航外跳高德地图或百度地图；不计算产品内路线和预计用时。

### 明确不做

- 话题系统、评论回复/楼中楼、关注、私信、复杂通知、跨章节或个性化推荐算法。MVP 包含章节分享爱心、单层评论和频道内有效阅读数排序。
- 十万次累计共读展示、重复识别/后台合并、运营后台和核心人物标记 UI。
- MVP-1 不实现站内活动报名/RSVP、活动日历、签到、成员名册及线上共读管理；站内报名明确列入 MVP-2。MVP-1 道场资料可保留已有外部报名说明/链接。
- AI 数据摄取、知识库索引、转写、摘要、问答和 Agent Harness 工程自动化。
- 管理员直接修改业务数据库之外的后台操作界面。必要的人员标签先留在后续需求中。

## 3. 开工前技术核对（Phase 0）

这些是有明确方向、但需依据现有实现作最后落地的事项；核对结果应补为 ADR 或更新本计划后再创建应用代码。

1. **仓库与家谱项目实现盘点**：核对 Node 版本、React 构建方式、Vercel Function 路由、Express 本地代理、workspace、Prisma 版本、认证模块边界、短信/邮件 provider 和媒体适配方式。
2. **隔离资源**：创建独立 Neon project/database 与开发/Preview/Production 环境；确定独立媒体存储账号/桶/凭据及生命周期。仅复用代码/技术，不复用实例、桶、账号或数据。
3. **地点与 POI 关联**：地点仅用于关联有效 POI 并在地图显示。用户拒绝定位或无法确认有效 POI 时，允许不带地理位置提交；该分享仍正常进入所属章节频道，只是不关联地图 POI。不得把临时地点强制作为分享或章节频道发布的前置条件。复用已验证的地图/POI 方案，不重新扩大为附近定位功能。
4. **媒体约束 ADR**：依据家谱项目实现选择同类技术并明确独立资源；确定允许媒体类型、上传大小/时长、格式、文件校验、公开读取和删除行为。媒体对象不能依赖不可撤销的永久公开 URL；隐藏后应停止应用端访问，且每次媒体读取须依据数据库最新状态作授权；已签发但未过期的对象存储直链不足以满足立即隐藏。上传通过签名或受限授权，不经常规 API 转发大文件。
5. **经典资料准备**：使用用户已提供的经文来源及章节资料，记录来源、版本和使用说明；不另行替换为未经确认的网络版本。将章节内容作为独立、可替换的数据集导入，不把经文硬编码进页面组件。
6. **部署和密钥**：建立独立 Vercel 项目/环境与部署配置；确认 Neon pooled/unpooled 连接、邮件/短信服务凭据、JWT/HMAC、地图服务凭据和媒体凭据的环境变量清单。
7. **密码恢复口径（已确认）**：手机号账号可用短信验证码重置密码，同一账号每滚动 24 小时最多成功重置一次；邮箱注册账号通过已验证邮箱重置。恢复邮箱为手机号账号的可选备用方式。短信发送另设服务端成本与反滥用限流。

## 4. 目标架构

按已确认的 Node.js + React 18 + Vercel + Express（本地）+ Prisma + Neon 方向，采用模块化单体：

```text
Responsive React app
       │ same-origin API
       ├── local: Express transport shell
       └── production: Vercel Functions
                    │
             shared handlers/services
               ├── auth adapter
               ├── domain modules
               ├── Prisma ── dedicated Neon DB
               ├── MediaStorage adapter ── dedicated object storage
               └── Geolocation/Maps adapter ── approved provider
```

沿用现有家谱项目实际构建与目录模式；不在未核实前把 CRA、具体 Node 小版本或某一媒体/地图供应商写死。浏览器不直连数据库或持有服务端密钥。数据库迁移以受控命令执行，不放进 Vercel build 隐式运行。

## 5. 分阶段编码计划

MVP-1 另含建议/VOC 最小闭环：登录用户与游客均可提交建议，提交内容自动持久化至数据库，登录用户可关联账号、游客身份可空；本期不做自动分类、摘要或 Agent 处置。

### 阶段 0：范围冻结与核对

- 确认 [MVP-1 编码前基线](./mvp-1-readiness-baseline.md) 及其决策/验收 Case ID。
- 任务指令明确业务规则以最新基线为准，原型用于页面结构和交互参考；第一批工作更新原型中地点、排序、媒体和来源的旧表述。
- 完成第 3 节代码、资源和内容来源的只读盘点。
- 在应用 schema/migration 之前，单独创建并评审数据库设计 Slice；数据库设计尚未启动，不能直接按旧预研草案落表。
- 匿名阅读切片先使用现有章节数据，可在数据库设计完成前开发；真实账号、分享和 VOC 持久化须先通过数据库设计评审。
- 更新架构 Spec 中被核实的运行时版本、构建命令、API 部署模式和媒体/地图 provider。
- 形成环境变量清单、数据备份/逻辑删除说明和原文导入说明。

**验收**：关键外部依赖有具体选择；独立数据库和媒体资源可供开发使用；经文种子数据有来源记录；未决项不阻塞基础应用初始化。

### 阶段 1：应用基础与账号

账号认证属于重要能力，但交付优先级低于匿名读书体验和信息框架；登录/注册必须支持受限写操作触发并在完成后回到原操作。

- 初始化响应式 React 前端及 Vercel API 入口；按现有项目建立本地 Express 传输壳和共享 handler。
- 根据已评审通过的数据库设计 Slice 创建独立 Prisma schema、Neon 迁移流程和环境配置。
- 从家谱项目迁移/抽取可复用认证代码到独立 `auth-kit` workspace，移除业务耦合并配置独立 provider 密钥。
- 实现手机号/邮箱验证码注册、手机号或邮箱密码登录、登出/会话读取、限流和密码找回。
- 手机号注册不要求邮箱；手机号账号可通过短信验证码重置密码，同一账号每滚动 24 小时最多成功重置一次。登录后的个人资料可选绑定并验证恢复邮箱作为备用找回方式。
- 密码重置须在服务端原子校验账号额度，只有成功重置后才消耗每日额度；验证码发送、失败验证与重置尝试实施独立限流，避免多设备并发绕过或产生不受控短信成本。达到额度时显示下一次可重置时间。
- 支持公开只读路由；发布、活动提交和道场维护 API 必须校验登录用户。

**验收**：匿名可访问公开路由；验证过的手机号或邮箱用户可完成注册登录和密码找回；手机号用户可通过短信验证码重置且每滚动 24 小时最多成功一次；可选绑定并验证恢复邮箱后也可通过邮箱重置；认证凭据不进入浏览器持久化的非必要位置；开发/Preview/Production 配置隔离；代码路径不引用家谱数据库或认证数据。

### 阶段 2：经典阅读与可替换内容数据

- 定义版本/章节数据结构，导入现有 1—81 章数据及其真实来源元数据；未确认底本不标记为王弼本。
- 实现“读书”默认 Tab、目录、章节阅读、上一章/下一章、字号调整和进度记忆。
- 为手机底部三 Tab（读书、发现、我的）及桌面响应式布局提供共用导航结构。
- 章节正文、来源、版本和后续替换采用数据读取，不把单一版本写死在 UI。

**验收**：匿名用户在窄屏和桌面均可打开 81 章目录并阅读；每章数据有可追溯版本/来源；替换或追加 TextEdition 不需重写页面组件。

### 阶段 3：账户资料、道场及定位发现

- 实现用户公开 profile 的最小字段和当前账号拥有权校验。
- 实现固定道场 CRUD：创建者维护名称、城市、介绍、活动方式、公开地址/联系方式；创建者关系可审计。
- 用户主动关联 POI 时可请求前台定位；定位数据仅用于 POI 关联，拒绝定位仍可无地点提交。
- 分享/记录可选关联有效 POI；无定位或无有效 POI 时不附地图关联，章节内容仍可正常发布。
- 实现“发现”Tab 道场地图/列表、按省市浏览固定道场和有有效 POI 的临时地点，并明确区分类型；章节分享从对应章节频道发现，不在 MVP 建设全局分享信息流。
- 定位仅在用户主动选择 POI 时请求；拒绝或无法确认 POI 时可继续无地点提交。

**验收**：道场创建者可维护自己的道场，其他账号不能越权修改；用户主动关联 POI 时授权后可匹配有效 POI；拒绝时明确提示且允许无地点提交；已选有效 POI 与无地理关联状态可区分；不请求后台持续定位。

### 阶段 4：共读提交与章节分享互动

- 实现单章节共读记录提交。一次活动提交一个章节；服务端生成分钟级 `submittedAt`，以 UTC 存储并按 Asia/Shanghai 展示，客户端时间不作为权威值。
- 每条活动记录必须指定唯一领读人；若领读人有账号则关联账号 ID，否则保存名称快照。提交人不自动等于领读人；公开展示前告知领读人姓名会公开。
- 一次活动只提交一个章节。每次已登录用户提交都保留原始记录，不做重复检测、合并、管理界面或独立活动统计；前端不显示提交数。
- 网络重试使用幂等键避免同一个 HTTP 请求重复创建记录。用户再次主动提交产生一条新的原始记录，保留供未来审计。
- 实现章节分享：文字必需，关联章节；分享作者固定为当前登录用户；可选关联道场/共读记录/来源 URL。分享卡片仅展示用户基础名称和头像。
- 实现有效阅读事件与曝光区分、去重统计和账号唯一爱心/单层评论；频道默认按有效阅读数降序，可切换最新。同一访客对同一分享按 Asia/Shanghai 自然日去重，累计计数不清零；阅读触发条件、访客键、异常流量与并列次序在开发本 Slice 前定义。
- 评论使用纯文本、限长、限频；评论作者可删除本人评论，分享隐藏/删除后关联评论立即停止公开读取。评论数据可为未来数据分析留存，但 MVP 不接入模型、不作为 AI 训练授权。
- 提供约 10 个内置 Q 版《道德经》风格默认头像；注册不要求用户先完成头像选择，Profile 后续可更换。默认自动分配方式在设计稿中确定。
- 实现可选音频、图片原始文件上传到独立媒体存储；数据库保存元数据和对象引用。首期不主动引导现场视频上传。媒体发布默认公开；每次读取依据数据库最新显隐状态放行，包含 Range 请求和缓存命中，不能向客户端提供绕过状态检查的对象直链。
- 发布者可隐藏自己的内容；隐藏立即从匿名公开查询、发现结果和媒体读取授权中移除。删除执行逻辑删除，不物理清除必要审计/tombstone；后续如单独立项 AI 能力，必须过滤。
- 为公开内容提供来源、作者、章节与提交时间展示。

**验收**：未经登录不能提交记录/分享或发表评论；单次共读记录只对应一个章节；同一活动的多人提交分别保留；同一 HTTP 请求重试不重复创建记录；产品页面不显示共读提交数；分享卡片展示基础名称和头像，不暴露联系方式；有效阅读按定义去重、爱心每账号唯一、评论仅单层并可由作者删除；有效阅读数/最新排序可切换且只作用当前章节；普通用户只能管理本人内容，管理员可管理所有用户内容且操作有审计；隐藏内容及其评论立即从公开查询和媒体访问中移除，逻辑删除后公开 API 不返回。

### 阶段 5：道场发现、发布闭环与部署准备

- 完成“发现”中的道场地图/列表和省市筛选；公开分享通过章节阅读/频道浏览，不提供全局信息流或个性化推荐。
- 道场详情须呈现常规共读时间规则、是否欢迎初次参与者、是否公开联系方式及外部报名说明/链接，让新人能判断何时前往和如何联系；不在 MVP 内实现站内报名。
- 完成“我的”中的个人资料、本人分享/共读提交列表和隐藏操作。
- 完成公开状态和定位说明、媒体上传状态、错误/空状态和授权拒绝提示。
- 配置 Vercel Preview/Production、数据库迁移、媒体上传域名/CORS、健康检查和基础错误日志脱敏。
- 编写运维手册：备份恢复、迁移回滚、媒体对象孤儿清理、逻辑删除、凭据轮换和人工数据库变更记录。

**验收**：从匿名阅读 → 注册登录 → 发布章节分享/共读记录 → 道场/城市/章节发现 → 隐藏本人内容的核心闭环可用；部署配置与数据资源独立；日志不含密码、验证码、完整 token 或签名 URL。

### MVP-2：站内活动报名（MVP-2 独立 Feature）

道场报名方式目前分散在外部微信小程序接龙。后续单独评审站内活动/报名 Feature：需要先明确活动日历来源、主理人发布权限、名额与候补、取消/变更通知、联系方式暴露和线下安全责任。不能将当前“活动记录提交”误作预告或报名。

## 6. 数据模型落地提示

概念边界以[技术架构 Spec](./technical-architecture-spec.md)为准。数据库设计尚未启动；本计划不引用未批准的表字段、索引或约束。数据库设计评审后再更新落地提示。

- `UserAccount` 与公开 `UserProfile` 分离；手机号/邮箱认证身份不充当用户公开资料。
- `TextEdition` 与 `Chapter` 数据化；章节内容版本可切换。
- `Dojo` 固定道场与 `TemporaryPlace` 临时地点分开。
- `GatheringSubmission` 每次提交一条；一个章节一条；`submittedAt` 由服务端写入。
- `ContentItem` 章节分享与经文正文分离；作者来自认证用户 ID。
- `MediaAsset` 只存元数据和独立对象存储键；隐藏/逻辑删除状态参与所有查询过滤。
- 不实现合并后台，但保留后续建立重复/归并关系所需的稳定 ID 和来源字段；MVP 不预建复杂统计域模型。

## 7. MVP 交付验收总表

| 区域 | 最低验收结果 |
| --- | --- |
| 阅读 | 匿名移动/桌面浏览 81 章，版本来源可见 |
